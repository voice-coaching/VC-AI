# 영상 분석·피드백 지연 관측과 시간 단축 계획

## 계획 수립 당시의 범위와 상태

계획 수립 요청에서 수행한 작업은 운영 기록 조회와 계획 작성이다. 분석·GPT 재실행, 운영 설정 변경,
재시작, PR·배포는 수행하지 않는다. 사용자 원문·영상·프레임·비밀값을 문서에 넣지 않는다.

조회 대상은 J406의 독립 영상 spool과 내부 canonical 작업 디렉터리다.
운영 revision은 `ac7cba9fe053abe7ac69946eeee30d8c82a3f761`로 확인했다.
정확한 조회 UTC와 숫자 영수증은 로컬 비공개 파일
`/home/2020067/video-latency-20261111-evidence.json`에 보관한다.

독립 경로의 완료 영상은 9건이며 최근 완료 3건을 비교했다. 내부 canonical 경로에서는
완료된 영상 요청을 찾지 못했다. 최신 음성 요청을 영상 요청으로 섞지 않았다.
최근 운영 영상 3건은 모두 **직전 속도 개선 배포 이전** 실행이다.
현재 배포본의 운영 영상 성능이 이미 측정됐다는 뜻으로 사용하지 않는다.

## 최근 운영 영상의 시간

완료 시각은 기존 `worker-complete.json`의 파일 수정 시각을 UTC로 표시했다.
단계 시간은 그 파일의 monotonic elapsed 값이다. 짧은 작업 표지는 디렉터리 UUID 앞 8자다.

| 단계·기록 | 최신 4802d023 | 이전 1d035c6c | 이전 3eda0a83 | 평균 |
|---|---:|---:|---:|---:|
| 완료 UTC, 2026-11-09 | 08:15:26 | 07:14:17 | 07:07:19 | — |
| 원본 영상 정규화 | 10.885초 | 4.058초 | 3.915초 | 6.286초 |
| 음성·영상 병렬 처리 및 입술 결합·CORE 기록 | 14.770초 | 13.811초 | 18.073초 | 15.551초 |
| GPT 포함 피드백 생성·응답 해석·관련 기록 | 16.463초 | 14.256초 | 13.777초 | 14.832초 |
| 검산·최종 결과 기록 | 0.798초 | 0.813초 | 0.764초 | 0.791초 |
| **기록된 위 4개 단계 합계** | **42.915초** | **32.939초** | **36.528초** | **37.461초** |
| 작업 생성 → worker 완료 파일 시각 | 45.139초 | 35.413초 | 39.691초 | 40.081초 |
| 병렬 구간 중 영상 추출, 위 합계에 추가하지 않음 | 11.489초 | 8.753초 | 9.986초 | 10.076초 |
| 병렬 구간 중 음성 처리, 위 합계에 추가하지 않음 | 14.651초 | 13.676초 | 17.995초 | 15.441초 |
| 피드백 구간 중 순수 provider 통신 | 15.881초 | 13.794초 | 13.245초 | 14.306초 |
| 음성 구간 중 MFA | 9.970초 | 9.089초 | 12.711초 | 10.590초 |
| 음성 구간 중 GOP, 당시 MFA 뒤 순차 실행 | 3.182초 | 3.017초 | 3.015초 | 3.071초 |

생성→완료에는 업로드·접수 대기·worker 시작 등이 들어간다. 단계 합계와의 차이인
2.224/2.474/3.163초를 어느 한 단계로 단정하지 않는다. 브라우저 업로드 시작 전 구간,
프론트 polling과 화면 표시 시간은 측정하지 못했다. 세 건은 ACK로 updatedAt이
추가 변경된 기록이 없지만, 완료 정렬에는 updatedAt 대신 완료 영수증 시각을 사용했다.

## 원인과 이미 반영된 개선

### GPT와 GOP: 재구현할 작업이 아니다

운영 3건은 GPT가 평균 1,562토큰을 출력했고, GOP와 MFA 중첩은 0초였다.
직전 배포에서 이미 feedback-only 응답과 internal GOP/MFA 중첩을 적용했다.
원본 Seungun JSON은 계속 전부 입력하고 서버가 확정한 점수표의 출력 복사만 없앴다.

현재 배포본과 같은 tree의 기존 시험 영상 영수증 `vl2v1`, `vl2v2`는 다음과 같다.
새 시험을 실행한 것이 아니라 배포 전 남긴 영수증을 읽었다.

| 현재 배포본의 지정 시험 기록 | testvideo1 | testvideo2 |
|---|---:|---:|
| 정규화 | 1.732초 | 1.754초 |
| 병렬·입술 결합·CORE 기록 | 14.338초 | 14.196초 |
| 그중 음성 / 영상 | 14.228 / 11.745초 | 14.111 / 6.885초 |
| GPT 포함 피드백 | 5.317초 | 4.170초 |
| 그중 순수 provider 통신 | 4.807초 | 3.823초 |
| GPT 출력 | 330토큰 | 337토큰 |
| 검산·최종 기록 | 0.761초 | 0.610초 |
| **기록된 4개 단계 합계** | **22.148초** | **20.731초** |

시험과 운영은 서로 다른 영상이다. 37.461초와 시험 평균 21.439초를 비교해 운영
개선율로 발표하지 않는다. 신규 운영 영상이 쌓이면 현재 revision으로 별도 집계한다.

### 정규화: 병렬 처리 앞에 있는 직렬 비용

[정규화 코드](../../src/voice_coach/backend_analysis/browser_video_normalize.py)는
원본 검사·probe·audio clock 조사·canonical MP4 생성·그 MP4의 PCM 추출·최종 probe를 수행한다.
최신 영상은 1080×1920으로 정규화됐고 10.885초를 썼다. 나머지 두 건은 480×720이다.
세 건 모두 tracksPreserved=false다. 앞 두 건은 sourceAudioClock.requiresRegularization=true다.

현재 코드는 영상 자체가 복사 가능해도 오디오 clock 보정이 필요하면 영상까지
재인코딩하는 분기로 들어간다. 다만 과거 영수증에는 원본 codec·회전·FPS별 분기 이유가
모두 없으므로, 앞 두 건에서 오디오 clock만이 재인코딩 원인이었다고 단정할 수는 없다.

### MFA: 실제 정렬보다 준비가 오래 걸린다

현재 배포본 시험 두 건에서 MFA는 각각 12.029/12.060초다.
저장된 `mfa_receipt.worker.performanceSpans`의 평균은 다음과 같다.

| 포함 관계가 있는 MFA span | 평균 wall 초 | 판단 |
|---|---:|---|
| setup | 8.596 | load_corpus 등을 포함 |
| load_corpus | 8.086 | dictionary·text·feature 준비 등을 포함 |
| dictionary_setup | 1.983 | 재사용 가능한 정적 준비가 있는지 조사할 후보 |
| normalize_text | 1.190 | 요청별 텍스트 작업·정적 초기화를 분리 조사 |
| generate_features | 1.712 | 실제 음성 특징은 매 요청 계산 유지 |
| align_utterances | 0.156 | beam을 줄일 우선 근거가 아님 |

setup/load_corpus의 processCpuSeconds도 wall과 가깝다. 이 두 시험에서는 단순 외부
네트워크 대기보다 CPU 준비 비용의 비중이 크다는 근거다. 단, 자식 프로세스 CPU와
미계측 내부 함수 전체의 원인을 이 값 하나로 설명할 수는 없다. **중첩 span은 합산하지 않는다.**

### 영상 모델: 이미 병렬이며, 다음 병목이 될 수 있다

[병렬 서비스](../../src/voice_coach/visual_feedback/canonical_service.py)는 음성과 영상 추출을
동시에 실행한 뒤 음소 정렬과 입술 관측을 결합한다. 현재 시험에서는 음성이 더 느렸다.
영상 분기만 3초 줄여도 현재 전체 시간이 3초 줄어드는 것은 아니다.

현재 시험의 음성-영상 시간 차는 2.483초와 7.226초다. 영상 분기가 그대로라면
음성 최적화만으로 병렬 구간을 줄일 수 있는 상한도 각각 이 차이 정도다.
따라서 MFA 준비를 줄이는 것과 영상 분기의 여유를 확보하는 작업을 함께 설계한다.

## 수행 순서와 변경 계획

### 1. 누락된 시간과 재인코딩 사유를 먼저 계측

- [worker](../../src/voice_coach/backend_analysis/independent_av_worker.py)에 정규화 전 준비,
  음성·영상 join 이후 입술 결합, 검산, 파일 기록을 분리한 span을 추가한다.
- 정규화에 원본 검사, 초기 probe/clock, remux 또는 video encode, canonical AAC decode,
  최종 probe/hash 시간을 나눈다. video/audio 각각의 복사 여부와 분기 사유 enum을 기록한다.
- [영상 포트](../../src/voice_coach/visual_feedback/adapters/canonical_video_features.py)에
  canonical probe, 모델 준비, decode·프레임 처리, PCM 검증, 종료 정리 시간을 추가한다.
  decode와 worker는 파이프로 겹치므로 별도 wall span과 중첩 여부를 표시한다.
- created/enqueued/worker-start/normalization-end/analysis-end/result-ready를
  내부 영수증에 남겨 업로드·큐·Python 시작 비용을 구분한다. ACK 시각과 완료 시각은 분리한다.
- 고정한 숫자·횟수·enum·revision만 기록한다. 대본·프레임·프롬프트·응답·키는 기록하지 않는다.

### 2. 정규화에서 불필요한 영상 재인코딩을 분리

- video stream-copy 가능 여부와 audio clock 보정 필요 여부를 별도로 판정한다.
  H.264/HEVC·회전·크기·FPS 등 기존 영상 조건을 모두 만족하면 video는 copy하고,
  필요한 audio track만 기존과 같은 방식으로 보정·AAC 인코딩하는 후보를 만든다.
- 영상 변환 자체가 필요한 입력에는 현재 경로를 유지한다. 실제 source codec과 분기
  사유가 확인되지 않은 건에서 무조건 copy를 선택하지 않는다.
- PCM은 계속 **최종 canonical MP4의 실제 AAC를 디코딩**해 만든다. 인코딩 전 PCM으로
  대체해 sample-exact A/V 검증을 깨뜨리지 않는다. 공통 PTS·A/V offset도 보존한다.
- 정규화 receipt revision과 AI 내부 검증기를 함께 갱신한다. 공개 API 필드명은 유지한다.
- canonical PCM과 음성 수치·정렬·점수 동등성을 확인한다. 영상 copy 전후의 decoded frame·PTS,
  입술 특징·점수·coverage·reason 변화도 대조한다. 기존 허용 오차를 넓혀 통과시키지 않는다.
  동등성이 확보되지 않은 분기에는 최적화를 적용하지 않는다.

이 작업은 병렬 처리 전에 있는 비용을 줄이므로 해당 입력에서 전체 시간에 직접 반영된다.
현재 10.885초 중 절감 가능한 양은 세부 계측과 같은 영상의 비교 전에는 확정하지 않는다.

### 3. MFA의 정적 준비와 요청별 계산을 분리

- load_corpus 안의 사전 준비·DB 구성·텍스트 처리·기타 Python CPU 비용을 세분화한다.
- 해시로 고정된 사전·모델의 불변 자료만 resident에서 준비할 수 있는지 검토한다.
  요청별 utterance·정규화·feature·alignment·출력·provenance는 분리해 새로 생성한다.
- DB를 재사용한다면 읽기 전용 정적 템플릿과 요청별 작업 DB를 분리한다.
  기존 요청의 음성 특징·음소 시간·CORE JSON·점수를 다른 요청에 재사용하지 않는다.
- 모델·사전·MFA 버전·관련 설정에 캐시 identity를 결속한다. 정적 자료 변경 시 새 generation을 쓴다.
- 첫 목표는 setup 평균 8.596초 중 2초 이상을 줄이는 후보를 찾는 것이다. 구현 전 보장값이 아니다.
  실제 전체 절감량은 영상 분기의 길이 때문에 이보다 작을 수 있다.
- beam/retryBeam, 1 job/BLAS 설정, Native/GOP·운율 계산은 이 단계에서 바꾸지 않는다.
  실제 정렬 0.156초를 줄이려고 정렬 정확성을 희생하지 않는다.

### 4. 영상 분기 최적화는 측정된 하위 병목부터 적용

- ffprobe 후 독립적인 landmark 추출과 canonical PCM 검증을 겹치는 후보를 검토한다.
  동일 descriptor/파일 identity·bounded output·timeout·자식 kill/reap을 유지하며 CPU 경합도 측정한다.
- 같은 요청의 최종 canonical probe 결과를 다시 쓸 수 있는지 검토한다. video SHA,
  probe 설정·도구 버전·요청/실행 identity에 결속하고 PTS·PCM 검증을 생략하지 않는다.
- [YuNet worker](../../src/voice_coach/visual_feedback/adapters/yunet_landmarks.py)는 요청마다 모델을
  초기화한다. 초기화 비용이 의미 있게 관측될 때만 모델 상주화를 검토한다.
  가중치만 공유하고 영상·PTS·랜드마크 버퍼·요청 상태는 분리하며 실패 시 generation을 종료한다.
- [feature worker](../../src/voice_coach/visual_feedback/adapters/canonical_feature_worker.py)는
  MediaPipe 장애 대응으로 허용 CPU 중 첫 CPU에 고정하며 YuNet 경로에도 이 제한이 적용된다.
  YuNet에서 제한이 필요한지 분리 실험한다. 현재 지연의 확정 원인으로 단정하지 않고,
  단일 native thread와 전체 자원 예산을 유지한 상태에서만 비교한다.
- 30FPS 관측 프레임을 줄이거나 음소당 최소 프레임 조건·얼굴 품질 기준을 낮추는 방식은 쓰지 않는다.
  검출기·mesh·AI-Hub 참조 모델을 교체하는 작업도 이번 속도 개선에 섞지 않는다.

### 5. 같은 입력으로 확인한 변경만 순차 배포

- 현재 revision의 지정 testvideo1/2를 기준으로 각각 비교한다. 운영 사용자 영상을 재실행하지 않는다.
  정규화 분기 검사는 지정 시험 영상에서 만든 세로 1080p/저해상도/회전/WebM/clock 경계 입력으로 보강한다.
- 음향·영상 분기의 성능 비교는 GPT 없이도 반복할 수 있다. 최종 후보는 요청당 GPT 1회·재시도 없이
  영상 2건과 AGENTS.md의 지정 음성·장애 7건을 검사하고 내부 request/result/handoff 읽기도 확인한다.
- 현재 tree·CORE/H5·모델·fixture SHA·cold/warm 여부를 기록한다. 같은 입력의 중앙값과
  범위·실패율을 비교하고, 동시 부하에서 queue/RAM/CPU와 지연이 악화되는지도 확인한다.
- 목표는 현재 배포본 대비 지정 영상의 전체 중앙 처리시간을 추가 15% 이상 줄이는 것이다.
  약 21.439초인 기존 시험 단계 합계 기준으로는 약 18.223초 이하다. 실제 신규 baseline으로
  다시 계산하며 2개 시험의 수치를 운영 p95/SLA로 부르지 않는다.
- 음성 관측·정렬·서버 점수와 공개 응답 형식을 유지한다. Seungun 원본 JSON은 생성된 바이트 그대로
  보관하고 GPT에 전달한다. 시간·UUID가 달라지는 별도 실행의 CORE 전체 바이트 일치를 요구하지는 않는다.
- 최종 점수·짧고 구체적인 피드백·입술 평가 범위와 근거가 유지되는지 확인한다.
  개별 음소 측정치를 프론트 공개 응답에 추가하지 않는다.
- 통과한 변경별로 새 CORE/H5·정규화 identity를 고정하고 PR·병합 후 coordinated 배포한다.
  모델 상주화 등 뒤 단계는 앞 단계 결과에 따라 선택하며 한 번에 모두 배포하지 않는다.

## 계획 수립 완료 판단

계획 수립 시점에서는 기록 확인과 계획만 완료했다. 새로운 속도 개선 코드나 운영 반영 완료로
보고하지 않는다. 실행 시 우선순위는 **세부 계측 → 정규화의 불필요한 인코딩 → MFA 준비 비용
→ 영상 분기의 새 병목**이다. 이미 배포한 GPT 출력 축소·GOP 중첩을 새 절감량으로 중복 계산하지 않는다.


## 계획 실행 후보

후속 구현 브랜치는 `perf/video-pipeline-20261111`이며 기준 main은 위의 `ac7cba9`다.
현재 운영 선택은 그대로 두고 새 `canonical_video_latency_internal_20261111_v1` CORE/H5를 만들었다.

- 정규화 v4는 복사·인코딩 이유와 하위 시간을 기록한다. 오디오 보정 시 영상 복사는 실험 인자로
  구현했으나 기본 경로에서는 활성화하지 않는다. 원본·공통 PTS·기존 영상 인코딩과 최종 MP4의 PCM을 보존한다.
- 영상 포트는 프레임 추출과 canonical PCM 검증을 병렬 실행하고 오류·취소 시 두 분기를 모두
  정리한 후 파일 descriptor를 닫는다. 선택적 시간 계측의 실패는 입술 평가를 중단하는 게이트로 쓰지 않는다.
- 내부 MFA에 저장소의 버전 고정 `PreparedDependencies`와 동등한 Core-row disambiguation helper를
  연결했다. 실행 파일·라이브러리·MFA 소스 identity를 검증하며 원래 SQL·갱신 순서와 요청별 DB,
  음성 특징·정렬·cleanup을 유지한다. 스레드·beam·모델·GOP 산식은 유지한다.
- MFA 내부 span, 정규화 하위 단계, 모델 초기화/프레임 처리, 작업 대기·결과 준비 시각을
  private 영수증에 추가한다. 점수·피드백의 공개 API 형식은 그대로다.
- 모델 상주화·CPU affinity 변경·probe 결과 재사용은 이번 후보에 섞지 않았다.
  먼저 추가 계측과 동일 시험 비교를 통과한 후보를 선택한다.

지정 영상의 정규화 비교에서는 두 건 모두 기존 COPY_ALL 경로였으며 PCM·디코딩 영상이 일치했다.
오디오 clock 보정 시 영상 압축 트랙 복사를 유지하는 분기는 실제 합성 MP4로 별도 확인한다.
최종 후보의 실제 분석·GPT·음성 회귀·수치 동등성 및 시간 결과는 완료 영수증에 결속한다.
두 영상의 서버 음성·입술 분석만 비교한 탐색 기록은 `/var/lib/intelligentai/voice-smoke/va2`다.
이 기록은 GPT 호출 0회이며 전체 피드백 생성 완료 검사로 표현하지 않는다.


### 점수 동등성에 따른 채택 결정

`va3`의 지정 testvideo1 오디오 보정 분기 비교에서 PCM·발음 평가·운율·음소 정렬·입술 coverage는
일치했으나 입술 점수는 기존 인코딩 83.6, 영상 복사 82.3으로 달랐다. 이 실험은 clock 보정 분기를
시험 조건으로 선택한 것이며 실제 사용자 영상의 재실행이 아니다. 영상 인코딩 변경이 mesh 입력
픽셀과 점수에 영향을 주므로 복사 분기는 **기본값 false인 실험 인자에만 남기고 운영 경로는 기존
인코딩을 유지**한다. 아직 이 분기의 속도를 운영 개선으로 합산하지 않는다.

현재 채택한 후보의 속도 개선은 정적 MFA 준비와 동등한 SQL 처리, 영상·PCM 검증 중첩에서 나온다.
DB 초기화 추가 조회와 새 span에서 DB 초기화는 약 0.07초였다. 요청별 DB 템플릿 캐시는 추가하지 않는다.
이미 검증한 기존 helper를 쓰며 원래의 요청별 상태·특징 계산과 검색 설정을 유지한다.
