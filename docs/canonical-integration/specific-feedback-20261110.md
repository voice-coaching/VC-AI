# 구체적인 음소·연습 피드백

발음 피드백을 길게 늘리지 않고 원고의 위치, 근거가 허용하는 소리의 차이, 실행할 교정 동작으로
구체화한다. [시스템 프롬프트](../../configs/coaching/six_dimension_system_v1.txt)의 practice 규칙을
수정했다. 특정 단어·좋은 답변 예시를 하드코딩하지 않는다.

## 작성 규칙

- 발음 정확성 항목은 확인된 단어·음절, 목표 자모와 초성/모음/받침 위치를 특정한다.
- 채택된 CLEAR_CONTRAST의 차이만 문제 양상으로 짚고 한 문장 안에서 교정 동작에 연결한다.
- GOP 경쟁 후보만으로 실제 대치나 생략을 확정하지 않는다. 이 경우도 목표 음소를 만드는
  구체적인 점검 동작을 안내하되 근거 부족·통계·면책 설명을 덧붙이지 않는다.
- 한국어 목표 음소의 일반적인 산출 지침은 연습 방법으로 사용할 수 있다. 그 지침을 사용자의
  혀·입술·기류를 실제 측정한 진단으로 표현하지 않는다.
- '또렷하게', '정확하게', '천천히', '비교하기'만으로 끝내지 않는다. 사용자가 입이나 읽기 방식을
  어떻게 바꿀지 알 수 있는 동작 하나로 대체한다.
- 전체 운율 요약으로 특정 단어의 실제 오류를 만들지 않는다. 원고의 짧은 구절은 연습 대상으로
  활용할 수 있지만 관측된 오류 위치와 구별한다.
- 영상에서는 해당 입술 평가 성분을 특정하되 기존 practiceScope와 관측·참조 한계를 유지한다.

길이 제한은 그대로다: 항목당 한 줄·한 문장, practice 98자 이하, 전체 최대 3줄·5문장·300자.
하위 세 항목 선정, 입술 우선순위, 점수·근거 ID·공개 API 필드를 변경하지 않는다.
새 내용이 길면 문장을 추가하는 대신 추상적인 표현을 동작 지시로 교체한다.

공개 화면에는 practice만 보인다. [최종 작성 규칙](../../configs/coaching/specific_feedback_final_v2.txt)을
조립된 프롬프트의 마지막에 둬, 채택된 대비가 있는 경우 목표 자모·다른 후보 자모·차이를
화살표 앞에, 교정 동작 하나를 뒤에 넣도록 명시한다. observation에만 문제 양상을 적은 결과는
표현 검사의 통과로 처리하지 않는다. 대비가 모호하거나 없는 경우 오류를 만들지 않고 목표
소리의 구체적 연습으로 작성한다.

## 패키징과 검증 범위

[프롬프트 전용 H5 빌더](../../deploy/dlpc/build_specific_feedback_h5.py)는 검증된
[v3 수식 후보](composite-exponential-v3.md)를 부모로 사용한다. 기존 prefix의 길이와 SHA를 확인해
시스템 프롬프트 기본부를 교체하고 최종 공개 문장 규칙을 마지막에 붙인다. v3 수식·발음 채점표·
CORE·영상 참조·GPT 요청 설정과 기존 프롬프트 부속문은 그대로 상속한다. 동결된 부모 패키지나
기존 결과를 덮어쓰지 않는다.

v3 H5는 인용 구절의 종결어미를 별도 지시로 오인하지 않도록 `bridge/pipeline.py`도 함께
고정한다. 정상적인 인용 구절을 포함한 한 문장에 `FEEDBACK_MULTIPLE_INSTRUCTIONS`가
발생하는 것을 오프라인으로 재현했다. 이 검사에서만 균형 잡힌 인용을 구분하며 실제 지시의
중복·문장 수·줄 수·길이 검사는 유지한다. 공개 문구 자체를 삭제하거나 고쳐 쓰지 않는다.

최종 v4 프롬프트는 모호한 근거에 대한 우선순위를 명시한다. 채택된 CLEAR_CONTRAST의 위치·
노출·경고 조건이 모두 맞는 경우에만 두 자모의 차이를 공개 문장에 넣는다. 다른 경우와 모델의
등가 음소 집합 내부 후보는 목표 자모 하나의 점검 연습으로 처리한다. 공개 문장에 경쟁 후보나
구별 과제를 억지로 추가하지 않는다.

직전 v3 후보의 실제 분석·GPT 9회 검사는 이전 프롬프트에 대한 기록이다. 새 프롬프트의 실제
피드백 검증을 대신하지 않는다. 최종 HEAD/tree에 결속된 음성/장애·영상 회귀와 음소 피드백
표현 검사를 별도로 기록한다. 합성 입력의 표현 검사는 음향 모델의 발음 검출 성능 검증이 아니다.
배포 완료 여부는 운영 영수증으로 별도 확인한다.

초기 프롬프트 후보의 합성 검사에서는 구체적인 동작을 만들었으나 소리의 대비가 observation에만
남았다. 이 후보의 구조 통과 영수증과 별도로 공개 내용 검토 실패를 보존했으며, 최종 규칙과 새
v2 H5로 수정했다. 이전 후보 검사 결과를 수정본 통과 기록으로 재사용하지 않는다.

작성 원칙 참고: [OpenAI 공식 prompt engineering 문서](https://developers.openai.com/api/docs/guides/prompt-engineering).
명시적인 출력 조건과 프롬프트 변경 시 평가를 활용한다. 모델·effort·API 방식은 변경하지 않는다.

## 2026-11-10 운영 JSON 활용 검토와 후속 로컬 수정

J406의 운영 revision `dfa3304425b4adf100efaf9f7c69ec9ec6936b5f`와 내부 H5 v4를
읽기 전용으로 확인했다. 최근 음성 분석 231·232·233의 보존된 CORE·원고·ASSESSMENT로
요청을 로컬 재구성한 결과, 세 요청 모두 기록된 `requestSha256`·`promptSha256`과
일치했고 마지막 user 메시지의 UTF-8 bytes도 CORE 원본과 일치했다. 이 검토에서
실제 사용자 작업을 재실행하거나 GPT에 재전송하지 않았다.

| 231 | 319707 | 427 | 515 | 10 | 57 |
| 232 | 305501 | 374 | 469 | 9 | 62 |
| 233 | 284586 | 300 | 421 | 10 | 63 |

원본 전달 누락은 확인되지 않았다. 다만 원본의 존재와 모델의 충분한 활용은 다르다.
운영 프롬프트는 실제 필드와 한계를 설명하지만 선정 항목별 원본 대조 순서를 강하게
요구하지 않았고, 공개 피드백은 전체 통계에 관한 일반적인 이어 읽기 지시로도 통과했다.
세 결과의 `naturalLanguageSemanticsFullyVerified`도 false다. 서버의 구조 검증을
자연어 품질 검증으로 해석하지 않는다.

세 요청은 발음 정확성이 하위 세 항목에 선정되지 않았다. 또한 GOP에는 모음 표본이
있지만 현재 위치별 경고 배열은 자음 중심이다. 233의 GOP 모음 표본은 23개인 반면
위치별 경고의 nucleus 레코드는 없다. 이 차이를 프롬프트가 누락된 모음 오발음을
만들어 채울 근거로 사용하지 않는다.

후속 로컬 프롬프트는 다음을 명시한다.

- ASSESSMENT의 항목별 direction과 COMPOSITE_WORKSHEET의 userValue·mean·std를 먼저 확인한다.
- 발음 표본·위치 근거·채택 상태를 대조하고 서로 다른 인덱스·음소 역할을 혼동하지 않는다.
- 쉼·속도에는 단어 정렬을, 음높이·강도에는 name으로 찾은 실제 곡선과 단어 정렬을 함께 확인한다.
- 국소 대응이 있으면 활용하고, 없으면 전체 측정 방향에 맞는 연습 구절을 선택한다.
- 발음 속도의 구절 진행, 조음 속도의 음절 간격, 쉼의 의미 경계를 서로 다른 동작으로 안내한다.

- 원고 인용의 글자·조사·순서를 보존하고 내부 판정 용어를 공개 practice에 남기지 않는다.
- 사용자 제공 예문은 프롬프트에 복사하지 않으며 기존 하위 세 항목·길이·점수·공개 계약을 유지한다.

이는 **후속 로컬 후보**다. 현재 소스의 프롬프트 파일을 편집한 것만으로 불변 운영 H5가
바뀌지 않는다. 기존 v4 H5나 결과를 덮어쓰지 않았고 새 H5 등록·PR·운영 배포는 수행하지 않았다.

## 후속 후보의 운영 패키징

운영 배포 요청에 따라 위 로컬 후보를 `canonical_actionable_coaching_*_20261110_v1_h5`로
별도 패키징했다. direct·internal의 기존 v4 H5와 비교하면 잠금 대상 중 시스템 프롬프트만
다르다. 원본 CORE·계산기·기준표·입술 참조·모델·effort·Standard 설정을 그대로 상속한다.
새 identity를 AI의 실행 허용·결과 검증·배포 복구 경로에 추가하며 과거 identity는 보존한다.
공개 응답 필드나 Frontend·Backend 코드는 바꾸지 않는다.

실제 배포 전에는 이 후보의 깨끗한 Git head/tree에 결속한 지정 음성·장애 7건, 영상 2건,
명확/모호 음소 표현 2건을 새 요청으로 검사한다. 앞선 합성 결과를 이 전체 검사 대신 쓰지 않는다.
운영 활성화 여부와 최종 revision은 배포 영수증에서 별도로 확인한다.
