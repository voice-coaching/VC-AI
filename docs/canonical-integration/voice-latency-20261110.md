# 음성 분석·피드백 시간 단축 계획과 구현

기준 main은 `441be7a396e832c035f55b7bf9cd68b40fc5f2ca`다. Seungun 원본 JSON의
생성·보관·GPT 전달, 서버 채점, 기존 공개 응답 이름, 피드백 3줄·5문장·300자,
Luna none/Standard와 요청당 GPT 1회·자동 재시도 없음 조건을 유지한다.

## 관측과 원인

최근 내부 음성 분석 231·232·233의 실행 시작부터 Backend 인계까지 평균은 34.30초였다.
업로드·접수 전 대기·프론트 polling·화면 표시 시간은 이 수치에 포함되지 않는다.

| 구간 | 평균 초 | 확인한 원인·한계 |
|---|---:|---|
| 예약·음성 확보 | 1.94 | Backend 예약과 저장소 읽기는 이미 병렬이다. 외부 왕복 포함 |
| CORE 준비·디코딩·Native/G2P·입출력 | 2.44 | 여러 준비·검증을 포함하는 잔여 구간. 순수 Native는 0.05~0.37초 |
| MFA | 11.11 | 정렬 workflow와 초기 feature 준비. 내부는 1 job/BLAS 1 |
| 정렬 후 근거 구성 | 0.68 | 운율·위치 정책·provenance 등. 순수 운율은 약 0.03초 |
| GOP | 4.13 | 내부 경로는 MFA 뒤에 CTC 가설 계산. 별도 음향 모델 추론은 없음 |
| 채점·요청 준비·GPT·응답 해석 | 11.64 | 이 운영 기록에는 순수 GPT 통신 시간 미보존 |
| 검증 | 0.63 | 원본·결합·점수 검산 |
| 게시 | 1.57 | 재검증·직렬화·영속 기록·외부 게시 |
| 근거 인계 | 0.17 | Backend HTTP 인계 |

운영 CORE를 대조하면 direct에는 GOP 중첩과 준비 최적화가 이미 있지만 internal에는
GOP 중첩이 없다. 전체 경로에 같은 최적화가 없다고 가정하지 않는다.

직전 지정 시험 `ac1w`의 실제 provider 관측에서는 입력 81,840~122,806토큰,
출력 1,163~1,476토큰, API 통신 9.98~12.18초였다. 입력은 원본 보존 요구에 따라
계속 전체를 전달한다. 서버에서 확정한 6항목·9항목 검산표를 GPT가 다시 복사하는 출력은
줄일 수 있다. [OpenAI 지연 최적화 문서](https://developers.openai.com/api/docs/guides/latency-optimization)는
출력 토큰을 줄이는 방법을 주요 개선 수단으로 설명한다. 이 가이드를 개별 요청의 속도
보장값으로 해석하지 않는다.

## 이번에 수행하는 단계

1. internal CORE에서 기존 Native logits와 full metadata가 준비되면 원래 GOP 함수를
   요청 소유 future 하나로 시작하고 MFA와 겹친다. 결과·오류 분류·float64 CTC·배치 32·
   MFA 설정을 유지한다. 완료·예외에서 future를 join하며 작업 종료는 기존 deadline guard가 맡는다.
2. GPT는 원본·점수·기준표·정렬·곡선을 모두 읽되 응답은 선정된 feedback만 생성한다.
   서버가 assessments와 기존 검산표 객체를 정확히 결합한 뒤 기존 전체 결과 검증을 수행한다.
   사용자용 practice와 선정·근거·영상 practiceScope 규칙은 바꾸지 않는다. GPT 응답에
   새 점수나 추가 필드가 있으면 임의로 수용하지 않는다. 점수는 기존 실패 정책대로 보존한다.
3. 내부 실행 로그에 provider POST 수·연결/통신 시간·토큰 수와 producer 단계 시간을
   허용 목록으로 남긴다. 원고·프롬프트·응답·키·헤더는 기록하지 않는다.
   MFA에는 포함 관계가 표시된 준비·setup·feature·정렬·정리 계측만 추가한다.
4. 같은 지정 음성의 baseline과 후보를 격리 실행해 비교한다. 최신 후보의 지정 음성·장애
   7건과 영상 2건을 실제 분석·GPT·검산·응답까지 검사하며 내부 request v4/result v6/handoff와
   Backend Java 읽기를 별도로 확인한다. 원본 바이트·수치 결과·점수·음소 위치를 대조한다.

1차 목표는 같은 시험 조건에서 중앙 처리시간을 25% 이상 줄이는 것이다. GOP 중첩의
최대 절감 예산은 약 4초이고 출력 감소의 실제 효과는 provider 관측으로 판단한다.
여러 원인·중첩 구간의 절감 상한을 그대로 더해 보장값을 만들지 않는다.

## 검증과 후속 선택 기준

- 실제 사용자의 기존 분석이나 GPT를 재실행하지 않고 지정 fixture와 승인된 장애 입력만 사용한다.
- 기존 결과와 새 CORE를 덮어쓰지 않는다. 새 CORE도 생성된 원문 그대로 GPT에 전달한다.
- 서로 다른 실행의 UUID·시각·처리 시간은 달라진다. 음향 관측·정렬·채점 값은 별도로 대조한다.
- 시간 비교는 같은 fixture·실행 경로끼리 한다. 서로 다른 원고의 운영 평균 34.30초를
  더 짧은 시험 문장과 비교해 개선율로 표시하지 않는다.
- 소수 시험의 중앙값은 운영 SLA/p95나 모든 화자·동시 접수 성능의 보장이 아니다.
- MFA 내부 캐시·BLAS 스레드·beam·모델 변경은 이번 계측 없이 동시에 적용하지 않는다.
  캐시 hit/miss와 실제 setup 비용이 확인된 후 음향 결과 동등성·자원 경합 검사를 거쳐 선택한다.
- 중복 preflight 제거는 요청·원본·실행 identity에 결속된 재사용 증명이 먼저 필요하다.
  시간을 줄이려고 검산·원본 검증·fsync·영속 결과 기록을 생략하지 않는다.
